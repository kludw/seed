# The Seed standard library

This directory holds the standard library ([docs/stdlib.md](../docs/stdlib.md)):
one directory per package, imported by its name (`import "json"`). The
compiler finds it next to its own binary (`<root>/lib`, or
`$SEED_ROOT/lib`) and looks there before the project's own packages.

- `io`, `net` and `fs.File` are native too, on top of the runtime's
  handle table and blocking calls (runtime/README.md, section 13), so that
  every wait in them is a stop point (and so are `os.run` and
  `os.output`).
- `fmt`, `os`, `fs`, `time`, `math`, `rand`, `crypto` and `regex` have native
  functions (declared without a body) written in C, in `<pkg>/<pkg>.c`,
  some on top of the runtime (`runtime/seed_pkg.c`, `seed_task.c`). How to
  write a native function is in
  [runtime/README.md](../runtime/README.md#13-native-functions).
- `errors`, `strings`, `path`, `encoding`, `json`, `http`, `csv`, `url`,
  `flags` and `log` are plain Seed; `time`, `math`, `rand` and `regex` are
  partly Seed (`regex`'s engine is native). `http` runs on top of `net`.

## Layout

```
lib/
  <pkg>/<pkg>.sd              the package (package <pkg>, pub API as in docs/stdlib.md)
  <pkg>/<pkg>.c               its native functions, if any (sd_lib_<pkg>_<name>)
  <pkg>/tests/<pkg>_test.sd   its tests (package <pkg>: test blocks)
  http/wire.sd                http's message reader and writer (no I/O)
  http/server.sd, client.sd   http.serve, serveListener, get, send, getWithin, sendWithin (on net)
  regex/regex_tables.c        regex's Unicode tables, generated by regex/gen/tables.go
  regex/gen/                  Go programs that generate regex_tables.c and tests/go_cases.sd
  COMPILER_BUGS.md            compiler issues found, with reproductions
  BUGS_FIXED.md               library bugs found by the QA pass, and how it tested
```

## Running the tests

```
make build/seed2
build/seed2 test lib          # every package (or: make test-lib)
build/seed2 test lib/json     # one package
```

Each package's tests are `test "description" { ... }` blocks in
`<pkg>/tests/*.sd`, which belong to the package (they can use private
names). `seed test` runs each test in a goroutine of its own and prints one
line per failure and a summary. Every file must be formatted (the compiler
checks it).

### Test conventions

- A check is `assert(cond)`; a comparison shows both values when it fails
  (`assert(got == want)`). An expected error is
  `assert(err != null)` followed by `assert(err.message() == "...")`;
  after `assert(err == null)` the values returned with `err` can be used.
- A crash test runs the code in a group and checks the crash message:

  ```
  fn crashRepeatNegative() {
      fmt.println(repeat("x", -1))
  }

  test "repeat negative crashes" {
      error err = group {
          spawn crashRepeatNegative()
      }
      assert(err != null)
      assert(err.message() == "crash: strings.repeat: count (-1) must not be negative")
  }
  ```

- Tests that need files work in `$TMPDIR` and remove what they made.
- `seed test` does not run under a leak checker. `tests/full/lib_*.sd`
  run packages end to end (regex, csv, url, flags, log), so `make
  test-leaks` covers them too; a package whose natives allocate should have
  one.
- Helpers in test files still carry the package's name as a prefix
  (`jsonTestError`, `httpTestParse`), from the time when the tests were
  merged into one namespace; that is no longer necessary.

### Conventions in the packages

- **Crashes.** A caller's mistake is reported with
  `os.crash("<pkg>.<fn>: <what is wrong>")` (docs/stdlib.md, "Errors and
  crashes"), which crashes the goroutine like a runtime fault: inside a
  group it fails the group.
- **Private names** are still prefixed in places (`jsonUtf8Len`,
  `httpIsToken`), from the same merged-namespace time.
- **Struct fields** are `pub` where docs/stdlib.md makes them public
  (`http.Request`, `http.Response`); `rand.Source.state` is private.
- **Doc comments.** Every `pub` constant, function, type and method has
  a `//` comment right above it, and every package has one right above
  the `package` clause of one of its files (`Package fmt writes ...`); a
  run of constants may share the comment above the first. `make test-lib`
  checks this (`seed doc --check lib`), and `seed doc <pkg>`, hover in
  editors and `make docs` (HTML in `build/docs`) show them. Comments right
  after the `package` clause are notes on the implementation, which
  `seed doc` does not show.

### fmt

`fixed(f, places)` is `snprintf("%.*f")`, which macOS and glibc round
correctly from the exact binary value (ties to even: `fixed(2.5, 0)` is
`"2"`, `fixed(0.125, 2)` is `"0.12"`); `nan` (of either sign), `inf` and
`-inf` are spelled out. Crash: `fmt.fixed: places (101) must be between 0
and 100`.

### os

- `output` is `run` with the child's stdout on a pipe (both ends
  close-on-exec, so concurrent children don't inherit them); the parent
  reads until end of file, then waits. Both waits are stop points
  (`sd_wait_fd`, `sd_wait_child`), as `run`'s is: a stopped goroutine
  kills and reaps the child (tests/full/os_stop_points.sd). Errors: `os.output: <program>:
  <reason>` when it cannot start (or reading or waiting fails); crash
  `os.output: argv is empty`.
- `hostname` is `gethostname`; error `os.hostname: <reason>`.
- `signals` drops repeated kinds, makes a `chan Signal` with room for one
  of each, and calls the native `watchSignal` per kind, which maps the
  enum's tag (its case index, in the order of os.sd) to the signal number
  and calls the runtime's `sd_signal_watch` (runtime/README.md, section
  11). Crash: `os.signals: no signals given`.
- `run` and `output` reject an `argv` with a NUL byte in any argument
  before starting anything (a C string would end there and run a
  different command): `os.run: sh\x00-c: program name contains a NUL
  byte`, `os.output: echo: argument 1 contains a NUL byte`.

### fs

- A path with a NUL byte is an error in every function (`exists` and
  `isDir` return false): `fs.read: a.txt\x00.png: path contains a NUL
  byte`, with each NUL shown as `\x00`. The OS takes C strings, so such a
  path would otherwise name the file before the NUL (`removeAll("d/\x00")`
  would remove `d`); Go fails the same way (`invalid argument`).
- `write`, `append`, `create` use mode `0644` and `mkdir` `0755` (before
  the umask), as docs/stdlib.md says; `write` and `mkdir` are therefore in
  fs.c rather than calling the runtime's versions, with the same messages
  (`fs.mkdir("")` is `fs.mkdir: : not a directory`).
- `append` holds a process-wide mutex around its `write` loop and opens
  with `O_APPEND`, so appends from goroutines never interleave (tested with
  5000-byte lines from two goroutines).
- `stat`: `size` is `st_size`; `modified` is `st_mtim` (`st_mtimespec` on
  macOS) in nanoseconds.
- `rename`'s error names both paths: `fs.rename: a -> b: <reason>`.
- `removeAll` uses `lstat`, so a symbolic link is unlinked and never
  followed. It reads all names of a directory before removing them. An
  error names the entry that failed: `fs.removeAll: dir/x/f: permission
  denied`. `removeAll("")` does nothing.
- `makeTemp` is `mkdtemp("$TMPDIR/<prefix>XXXXXX")` (trailing slashes of
  `$TMPDIR` removed; `/tmp` when it is unset or empty).
- **File handles.** A `File` is an entry of the runtime's handle table
  (runtime/README.md, section 13; kind `SD_HANDLE_FILE`), shared with `io`
  and `net`. It holds the entry's id, whether it was opened for writing,
  and the path (for messages, which keep the path after `close`). Ids are
  never reused, so a stale copy of a closed handle finds nothing (`file is
  closed`). The table's operation lock makes each operation atomic (a
  handle sent to two goroutines writes whole `write` calls). Descriptors
  are close-on-exec.
- `open` fails on a directory with `is a directory`. `readLine` and `read`
  share the handle's buffer; `read` returns what is buffered, or does one
  `read(2)` of at most 64 KiB. End of file is not remembered, so a file
  that grows can be read further. Messages: `fs.File.<method>: <path>:
  file is open for reading only` / `writing only` / `file is closed`; crash
  `fs.File.read: max (0) must be at least 1`.
- Reads poll before they read, so they are stop points (a FIFO nobody
  writes to can block for ever; tests/full/fs_file_stop.sd). `open`
  (which blocks on a FIFO until the other end opens it), writes and the
  whole-file functions make their system calls in interruptible block
  sections (runtime/README.md, section 13): a stop interrupts them while
  they wait (tests/full/fs_fifo_stop.sd); on a regular file they complete.

### time

- `now` is `CLOCK_REALTIME`; `monotonic` is the runtime's clock
  (`CLOCK_MONOTONIC`, the one its timers use).
- `Date`'s fields are `pub` (docs/stdlib.md now says so). `date`,
  `fromDate`, `format` and `parse` are Seed, with Howard Hinnant's
  days-from-civil formulas and floor division, so they work for any `int`
  (years before 0 and beyond 9999 included; tested against Python's
  `calendar.timegm` and with 2000 random round trips over ±3000 years).
- `fromDate` checks month, day (leap years included), hour, minute, second
  and nanosecond, in that order: `time.fromDate: 2026-02-29T00:00:00Z: day
  out of range`. The subject shows the fields as given.
- `format` crashes outside years 0–9999: `time.format: year (10000) must be
  between 0 and 9999`.
- `parse` is strict RFC 3339 as docs/stdlib.md describes. Errors: the
  range reasons above, or `expected a digit`, `expected '-'`, `expected
  'T'`, `expected ':'`, `expected 'Z' or an offset like +02:00`, `expected a
  digit after '.'`, `more than 9 fraction digits`, `offset out of range`,
  `unexpected text`, each followed by ` at offset N`. A leap second `:60`
  is `second out of range`; offsets must be at most 23:59.

### strings

- `padLeft`/`padRight` count characters as `s.chars()` does (an invalid UTF-8
  byte is one character); each `fill` byte counts as one character.
- `repeat` doubles the piece, so it does O(log count) concatenations.

### path

Go's `path` semantics; the rules and examples are at the top of
`path/path.sd`. Two edge cases docs/stdlib.md does not spell out:
`dir("a/b/")` is `"a/b"` (as in Go: the last element is the empty one after
the slash), and `ext` gives `""` for the bases `"."` and `".."` and `"."` for
`"a."`. `join([]string{"a", "/b"})` is `"a/b"`.

### math

`inf()` is written in Seed (`1.0 / 0.0`, IEEE); docs/stdlib.md now says so.
`minFloat`/`maxFloat` treat `-0.0` as smaller than `0.0` and return `nan`
if either argument is `nan`. `absFloat(-0.0)` is `0.0`. The other float
functions are one-line natives over the C library (math.c), so they give
exactly what C99 gives: `round` is C `round` (halves away from zero),
`sqrt(-1.0)` is `nan`, `log(0.0)` is `-inf`, `atan2(-0.0, -1.0)` is `-pi`.

The exponent parameter of `powInt` and `powFloat` is `exponent`, not `exp`
as docs/stdlib.md first had it: a parameter may not shadow a package-level
name, and `exp` is now a function. The crash reads `math.powInt: exponent
(-1) must not be negative`.

### encoding

- Errors: `encoding.<fn>: offset N: <reason>`, where a byte is shown as
  `'g'` when it is printable ASCII and as `byte 0xff` otherwise. Reasons:
  `invalid hex digit 'g'`, `odd number of hex digits` (offset of the last,
  unpaired digit), `invalid base64 character '-'`, `incorrect padding`,
  `input ends in the middle of a byte`, `'%' must be followed by two hex
  digits`.
- Base64 decoding with padding requires exactly the padding the last group
  needs (`Zg=` is an error). Unused bits in the last character are ignored,
  as Go's decoders do by default (`Zh==` decodes like `Zg==`).
- `urlDecode` keeps every byte other than `%XX` and `+` as it is.

### rand

The algorithm, fixed by docs/stdlib.md and made precise here (also at the
top of `rand/rand.sd`): SplitMix64 for raw output; `range` draws the
smallest number k >= 1 of 64-bit outputs with 2^(64k) >= n, joins them with
the first one most significant, and rejects values at or above the largest
multiple of n below 2^(64k); `fraction` is the top 53 bits times 2^-53;
`permutation` is Fisher-Yates from the end. The outputs for seeds 0 and
1234567 match the reference `splitmix64.c`.

64-bit wrapping arithmetic is emulated with `& 0xffffffffffffffff`, and the
products are ~128-bit big integers, so each step allocates. Measured on an
Apple-silicon Mac (`-O2`): **about 0.5 µs per 64-bit output (2 million per
second)**, and about 0.6 µs per `range(0, 100)`. A native `next` would be
much faster; it can replace the Seed one without changing any output.

The package functions `rand.range`, `rand.fraction` and `rand.permutation`
draw from a per-goroutine generator: the native `nextOs()` (rand.c) is a
SplitMix64 state in goroutine-local storage (`sd_goroutine_local`: a
goroutine may run on several threads), seeded with `getentropy` (or
`/dev/urandom`) on the goroutine's first use and freed when it ends. `Source` has
a private `bool fromOs` (false from `seeded`); when it is set, `next`
returns `nextOs()`, and each package function is
`Source{state: 0, fromOs: true}` followed by the method call, so the
algorithms exist once. Crash messages name the function that was called:
`rand.range: ...` for the package function, `rand.Source.range: ...` for
the method.

### crypto

Everything is native (crypto.c), as docs/stdlib.md says. `sha256` and
`hmacSha256` were first written in Seed (about 12 MiB/s); the C versions
pass the same vectors in `tests/crypto_test.sd` (FIPS 180-2 examples,
padding-boundary lengths 55, 56, 63, 64, 65, 119, 120 and 1000, the
one-million-`a` vector, and RFC 4231 cases 1, 2, 3, 4, 6 and 7).

- `randomBytes(n)` uses `getentropy` in 256-byte pieces, falling back to
  `/dev/urandom`. Crashes: `crypto.randomBytes: n (-1) must not be
  negative`, and `crypto.randomBytes: the OS provided no randomness:
  <reason>`.
- `equal` returns `false` at once when the lengths differ; otherwise it ORs
  the XOR of every pair of bytes through a `volatile` accumulator, so the
  time depends only on the length.

### json

- Parse errors: `json.parse: line L, column C: <reason>` (docs/stdlib.md's
  format; the column counts bytes). The reasons are listed at the top of
  `json/json.sd` and covered by tests, including hints for comments, single
  quotes and the byte-order mark.
- Strictly RFC 8259: no leading zeros, `+`, `.5`, `1.`, `NaN`, trailing
  commas, comments or BOM; control characters must be escaped; strings must
  be valid UTF-8 (overlong forms, surrogates and code points above
  U+10FFFF are rejected). `\uXXXX` is decoded with surrogate pairs; a lone
  surrogate becomes U+FFFD.
- Nesting deeper than 512 arrays and objects is an error; 512 is accepted.
- A number too large for a float (`1e400`) is an error, `number out of
  range`; one too small (`1e-400`) becomes `0`.
- Printing: whole numbers below 1e21 print as integers (`-0` for negative
  zero), others as `f.string()`; control characters are escaped as `\n`,
  `\t`, `\r`, `\b`, `\f` or `\u00xx` (lowercase hex); each byte of invalid
  UTF-8 becomes one U+FFFD; DEL is written as it is. Printing `nan` or an
  infinity crashes: `json.Value.string: nan cannot be written in JSON`.
- json uses only `errors` (plus `os` for `os.crash`), not `strings` and
  `math` as the dependency table in docs/stdlib.md allows.
- Printing appends to one string that grows in place (`w.out = w.out +
  ...` on the writer's field, which the compiler turns into an in-place
  append), with string runs between escapes copied whole and whole numbers
  written as digits straight into it. Parsing takes a string without
  escapes as one slice of the text (`str`); strings with escapes, and
  errors, are separate functions (`strRest`, `failValue`, `unexpected`), so
  the common paths need no cleanup frame. docs/performance.md, "JSON", has
  the profile.
- Measured: parsing and printing a 3.8 MB document takes about 0.15 s
  (~25 MB/s for parse plus print) before this; `bench/seed/json.sd` (1 MB,
  30 rounds) went from 0.71 s to 0.42-0.46 s on Linux x86-64 (Go: 0.75-0.80 s).

### io

Stdin is a handle of the runtime's table (kind `SD_HANDLE_STDIN`), so
`readLine`, `read` and `readAll` share its buffer, are serialised between
goroutines (each call is atomic) and are stop points. The descriptor is
left blocking (it may be shared with a terminal or another process), so
the runtime always `poll`s before it `read`s. Stdout is flushed before each
read. `read(max)` (added for `seed lsp`, whose messages are a header line
and a body of a given length with no newline after it) returns what the
buffer holds, up to `max` bytes, or else one `read` of the descriptor, like
`fs.File.read`. A `"\r"` is removed only directly before a `"\n"` (a last line
`"x\r"` without a newline keeps it). `io` has no `tests/` directory: what
it reads depends on the test runner's stdin, so it is tested by
`tests/full/io_stdin*.sd` (with `.in` files), by `tests/examples.sh`
(wordcount) and in C by `runtime/tests/test_block.c`.

### net

- Handles are `{int id}` structs with a private field; every operation
  looks the id up in the runtime's table, so a closed or copied handle is
  safe to use (it gets `connection is closed`). A closed listener says
  `listener is closed` (docs/stdlib.md only names the connection's text).
  Errors about a closed handle have no subject (the entry, and with it the
  address, is gone): `net.Conn.read: connection is closed`, except for a
  goroutine that was already waiting in the operation when the handle was
  closed (`net.Listener.accept: 127.0.0.1:5000: listener is closed`).
- `listen(":port")` listens on every IPv4 interface (`0.0.0.0`, as the
  doc's example shows); `listen("[::]:port")` for IPv6. `SO_REUSEADDR` is
  set, so a server can be restarted at once.
- `dial(":port")` dials `localhost`. Numeric hosts are not looked up;
  names are resolved in a helper thread, so that the timeout and a stop
  also cover name resolution (the lookup is abandoned and frees itself).
  Each resolved address is tried in order; the error is the last one's.
- Address mistakes are errors, not crashes (`missing port`, `invalid
  port`, `missing ']' in address`, `IPv6 addresses need brackets:
  [::1]:80`), because addresses usually come from outside the program.
- `listen` asks for an accept queue of 65535, which the OS clamps to its
  limit (`kern.ipc.somaxconn`, 128 by default on macOS; `net.core.somaxconn`
  on Linux), as Go does. On macOS a burst of more than about 150
  simultaneous connections can get `connection reset by peer`; Go's
  `net/http` does the same there (lib/BUGS_FIXED.md).
  `read(max < 1)`, `setTimeout(d < 0)` and `dial(timeout < 0)` crash.
- Sockets are non-blocking, close-on-exec, `TCP_NODELAY`, and never raise
  `SIGPIPE` (`SO_NOSIGPIPE` on macOS, `MSG_NOSIGNAL` elsewhere); writing to
  a closed peer is the error `broken pipe` or `connection reset by peer`.
- `read` returns at most 64 KiB per call whatever `max` is (the doc allows
  fewer bytes than `max`).

### http

`http.sd` has the public API. `server.sd` has `serve` and
`serveListener`, `client.sd` has `get`, `send`, `getWithin` and
`sendWithin`; both use `wire.sd`, which
is private and free of I/O:

- `MessageReader`: fed bytes as they arrive (`feed`), it returns
  `nextRequest()` → `NeedMore | Done(Request) | Reject(status, reason)` and
  `nextResponse(method, eof)` → `NeedMore | Done(Response) | Fail(reason)`.
  It is resumable, keeps bytes after a message for the next one
  (keep-alive, pipelining), and copies each byte a bounded number of times,
  so a large body arriving in small reads is linear (a 1 MB body in 4 KiB
  pieces is tested). The reading rules (line endings, header validation,
  framing, limits) are at the top of `wire.sd`.
- `responseBytes(method, resp, close)`, `errorResponseBytes(status)`,
  `parseUrl(fnName, url)` → `HttpTarget{address, host, target}`, and
  `requestBytes(fnName, req, target)`.

Decisions not fixed by docs/stdlib.md:

- `Request.path()` decodes `%XX` but keeps `+` (a `+` is a space only in
  queries). Empty query parameters (`a=1&&b=2`) are skipped.
- An HTTP/1.1 request without `host` is rejected with 400 (RFC 9112). Other
  rejects: 400 malformed, 413 body over 8 MiB, 431 headers over 64 KiB, 501
  a transfer-encoding other than chunked, 505 an HTTP version other than 1.x.
  A message with both transfer-encoding and content-length is rejected.
- Obsolete header folding is rejected. Header values have spaces and tabs
  trimmed and may not contain other control characters.
- `transfer-encoding` stays in the headers after the chunked body is decoded.
  Chunk extensions and trailers are ignored.
- Writing: header names are lowercased and invalid ones skipped; CR and LF
  in values become spaces (no response splitting); the server writes
  `content-length` itself and drops `content-length`, `transfer-encoding`
  and `connection` set by the handler; 1xx, 204 and 304 responses get no
  `content-length` and no body; an unknown status gets an empty reason
  phrase. The client keeps a `host` header the program set.
- Responses: 1xx interim responses are skipped; HEAD, 204 and 304 have no
  body; with neither length nor chunking, the body runs until the
  connection closes.
- No `date` header is written yet (`time` exists now; nothing uses it here).

The server and the client (server.sd, client.sd):

- **Stopping.** docs/stdlib.md's `serve` runs until its goroutine is
  stopped, and its port can't be chosen freely (port 0) because nothing
  reports it. `serveListener(net.Listener, Handler)` was added for that: the
  program listens, reads `ln.addr()`, and serves; closing the listener (any
  copy, from any goroutine) stops the server, which then returns `null`.
  Inside, the accept loop is a group block; when accept says `listener is
  closed`, the block spawns a goroutine that returns a private sentinel
  error, which fails the group and so stops every connection goroutine
  (requests in progress are cut off; there is no graceful drain).
- Each connection is a goroutine of the server's group; each request runs
  its handler in a group of its own (one more goroutine), so a handler
  error or crash becomes `500` with `internal server error\n`, logged as
  `http: GET /path: <message>` on stderr, and the connection carries on.
  Finished connection goroutines are freed while the server runs (the
  runtime reaps finished members of a group at each `spawn`).
- Timeouts: 60 s for the next request on an idle kept-alive connection, and
  30 s without progress while a request is arriving (docs/stdlib.md says
  30 s for the whole request; the server does not track that with
  `time.monotonic` yet, so a client trickling bytes can keep a connection
  longer).
- HTTP/1.0 requests close the connection unless they say `connection:
  keep-alive`; `connection: close` closes after the response. A request
  with `expect: 100-continue` gets `HTTP/1.1 100 Continue` before the server
  reads its body (curl waits a second for it otherwise), unless the body
  came with the head; the reader forgets the expectation once the request
  is complete, so no stray 100 reaches the next request. Rejected requests
  (`400`, `413`, `431`, `501`, `505`) get the status and its reason as a
  plain-text body, then the connection is closed.
- `serve`'s listen error and the client's network errors are rewritten to
  the http function's format: `http.serve: :80: permission denied`,
  `http.get: http://localhost:1/: connection refused` (the `net.dial:
  <addr>:` part is dropped). A malformed response is
  `http.get: <url>: malformed status line` and so on (wire.sd's reasons).
- A request's `timeout` (and `getWithin`/`sendWithin`, which set it;
  DECISIONS.md, "An HTTP request's time limit"): the
  limit runs from before the dial to the end of the response, on
  `time.monotonic`. The dial gets the whole limit (`net.dial`'s own
  timeout), and before every write and read the connection's timeout is set
  to what is left (`setTimeout`), checked again after each read, so no wait
  outlasts the deadline and a server that trickles bytes is cut off at it.
  Any `timeout` from net on the way becomes `<fn>: <url>: timeout after
  <limit>`. A write that keeps making progress past the deadline is the one
  thing that can overrun it (by as long as that write takes). With
  `timeout` 0, the default, `httpSend` has no limit: 30 s without progress
  per step, as before.
- The client writes the whole request before reading; a server that
  answers early and closes (413) while a large body is still being sent
  can make that a write error instead of the response.

### regex

`regex.sd` is the API; `regex.c` the engine (the overview is at its top),
`regex_tables.c` the Unicode tables.

- **Compiling.** A recursive-descent parser builds a tree with every class
  resolved to sorted rune ranges ((?i) folded with Go's `appendFoldedRange`
  and Unicode's simple folding orbits, `\p{..}` from the tables). The tree
  is compiled twice into byte-level NFA programs: forward with capture
  slots, and reversed without them. Rune ranges become UTF-8 byte
  sequences (the utf8-ranges splitting, sharing prefixes in a trie); the
  ASCII part of a class is one instruction with a 256-bit set. Counted
  repetition is expanded as Go's `syntax.Simplify` does, and `x*` of an `x`
  that can be empty is `(x+)?` as in Go's compiler, so the program has
  Go's priorities and leftmost-first matching picks Go's match and groups.
  Limits: repetition counts up to 1000, nesting depth 1000, 400,000
  instructions (`expression too large`).
- **Searching.** A lazily built DFA runs over the forward program; its
  states are thread lists in priority order plus what is known about the
  byte before (edge, newline, word, other: for `^ $ \b \B`), where a UTF-8
  character stands (new threads start only at character boundaries, as in
  Go), and whether a match was seen (which cuts lower-priority threads and
  stops new ones). The last position where a match ended is the end of the
  leftmost-first match. A second DFA runs the reversed program backwards
  from that end, longest match, to find the start. Only when the pattern
  has groups does a Pike VM run, anchored at that start, for the group
  positions. `matches` stops at the first match end. When no thread is
  alive and every match must begin with one of at most 32 bytes (no
  continuation bytes), the DFA skips ahead with `memchr` or a byte table.
  Each DFA state is built in time proportional to the program, at most one
  per byte read; the cache is flushed at 2 MB, so every search is linear in
  the text, whatever the pattern.
- **The cache.** A `Regex` is `{pattern, id, names}`, plain data. Compiled
  programs and their DFAs live in a 16-entry LRU cache in goroutine-local
  storage (`sd_goroutine_local`), keyed by the id (from a process-wide
  atomic counter); a goroutine that meets an id it has not seen (a Regex
  received over a channel, or evicted) compiles the pattern again. The
  cache is freed by an `sd_goroutine_atexit` hook when the goroutine ends.
  The natives never park, so the cache needs no lock.
- **Go compatibility.** `tests/go_cases.sd` holds about 3,100 patterns and
  texts with the matches Go's `regexp` finds (`FindAllStringSubmatchIndex`),
  hand-picked and random (`gen/cases.go`; `go run gen/cases.go 30000 SEED`
  makes a larger table for a one-off run: 120,000 more cases passed). Known
  differences, all deliberate or edge cases: duplicate group names are an
  error; `$1x` in a template; a truncated UTF-8 sequence is not matched as
  U+FFFD; and patterns where Go's prefix factoring drops a mid-group flag
  (`A(?i)x|Aa*`, which Go parses as `A(?i:X|A*)`).
- **Performance.** `bench/seed/regex.sd` (a 1.5 MB log: `findAll` with
  groups, `matches` per line, `replace`, `split`; five rounds) takes 0.59 s
  against 2.5 s for `bench/go/regex.go` on Linux x86-64.
- Regenerating: `go run lib/regex/gen/tables.go > lib/regex/regex_tables.c`
  and `go run lib/regex/gen/cases.go > lib/regex/tests/go_cases.sd`.

### csv

Pure Seed. `Reader.feed` is a line-by-line state machine (the record in
progress, the pieces of an open quoted field and where it opened); `parse`
and `parseMaps` split the text at `"\n"` and feed it. It agreed with Go's
`encoding/csv` (`FieldsPerRecord = -1`) on 3,000 random texts made of `a`,
`,`, `"`, `""`, `\n`, `\r\n`, `\r` and spaces.

### url

Pure Seed. `parse` splits as RFC 3986 appendix B (fragment, query, scheme,
authority, path), then checks each part: no spaces or control characters,
`%` followed by two hex digits, a numeric port up to 65535, and a host
without `[ ] / ? # @` (outside an IPv6 literal's brackets). The scheme is
recognised only if it is valid (a letter, then letters, digits, `+ - .`);
otherwise the text is a relative path, which may not have a `:` in its
first segment. `resolve` is section 5.2.2 with `remove_dot_segments`
(5.2.4); the tests have every example of section 5.4.

### flags

Pure Seed. A `Spec` is a list of `Flag`s (name, short name, kind, initial
`Value`, help); `Parsed` keeps a map of values and a map of the flags that
were given. The duration syntax and its formatting in the usage follow
Go's `time.ParseDuration` and `Duration.String`. Did-you-mean suggestions
use the edit distance (at most 2).

### log

Pure Seed. A line is built whole (with `time.date` for the timestamp, in
milliseconds) and written with one call: `fmt.eprint`, `fmt.print`,
`fs.File.write` (atomic through the handle's operation lock) or a channel
send. The fields of `with` are rendered once, when added.

## Inconsistencies found in the docs

- docs/stdlib.md says two `json.Value`s compare with key order counting, "as
  it does for maps", but DECISIONS.md ("Types and values") and the runtime make map `==`
  ignore insertion order. `Value`'s `==` is the built-in enum `==`, so key
  order is ignored; the json tests check that.
- The task brief asked for JSON errors with a byte offset; docs/stdlib.md
  specifies line and column, which is what the parser reports.
