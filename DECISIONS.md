# Decisions made without you

You asked not to be woken up, so these are the language and toolchain decisions that were made during the overnight build without you.

**How to read this.** Each line is one decision, in its final state: where a later decision replaced an earlier one, only the final one is listed (the history is in git). Every decision here is reflected in [SPEC.md](SPEC.md) and the documents it links to, which give the full rules. Nothing here is set in stone: anything can be reversed, and the line tells you what would change. Implementation details that don't affect how you write Seed are in [compiler/README.md](compiler/README.md#decisions) and [runtime/README.md](runtime/README.md#16-decisions-and-limitations).

## Syntax

- **No semicolons.** One statement per line; `;` only separates the parts of a `for` header.
- **Newlines end statements using Go's rule.** A line continues when its last token can't end a statement: an operator, `=`, `.`, a comma or an opening bracket.
- **Byte literals use single quotes:** `'a'`, `'\n'`, with the same escapes as strings. A lexer can't be written comfortably without them.
- **Float literals must contain a `.`** (`1.0`, `2.5e3`), so `1` is always an `int`. Integers are decimal or hex (`0xff`), of any size; no octal, binary or `_` separators.
- **A number never starts with `0` followed by a digit.** `017` is an error with the hint `write 17` (C and Go would read it as octal 15); `0`, `0.5` and `0x0f` are fine.
- **Names are ASCII.** Identifiers are ASCII letters, digits and `_`; any other character outside strings and comments is an error, reported once as the whole UTF-8 character.
- **Built-in type names (`int`, `string`, ...) are predeclared identifiers,** not keywords, and like every name they can't be declared again.
- **No raw or multi-line strings.** One way to write a string.
- **`?` applies to the whole type on its left.** `[]string?` is a nullable list; a list of nullable strings is `[](string?)`. So a nullable function type is `(fn(int) int)?`, and `fn(int) int?` returns `int?`.
- **`fn(int) f` vs `fn(int) bool f`.** Where a type is followed by a name, an identifier after a function type's `)` is its result type only if another name, `.` or `?` follows.
- **Several results: a typed name is declared, an untyped one is assigned.** `string text, err = fs.read(p)` declares `text` and reuses `err`.
- **No labels and no `goto`.** `break`/`continue` inside a `switch` or `select` apply to the enclosing loop.
- **Case bindings write their type** like every declaration: `case Shape.Rect(float w, float h):`.
- **A case without data has no parentheses,** in its declaration (`Eof`, not `Eof()`), as a value (`Token.Eof`) and in a pattern.
- **Comparisons don't chain** (`a < b < c` is an error), and `x += 1` gets an error with the hint `x = x + 1`.

## Types and values

- **`error` is the one type that can be `null` without `?`.** A null error means "no error".
- **Package-level variables are not allowed**, only `const`: goroutines share nothing, so there is no global mutable state.
- **Constants are computed at compile time:** literals, other constants, operators, conversions and value-only built-in methods (`name.len()`); no calls. They are allowed inside functions too, and cannot hold channels.
- **Map keys are limited to `int`, `byte`, `bool` and `string`.** Maps keep insertion order; map `==` ignores the order.
- **Map values can't be nullable** (`map[K](V?)`), because `m[k]` already returns `V?` with null for a missing key; for the same reason `m[k]++` is not allowed.
- **`m.getOr(k, d)` reads a map with a default** (a plain `V`; the map is not changed), so counting is one line, `m[k] = m.getOr(k, 0) + 1`, instead of a lookup, a null check and two assignments. It is a method rather than an operator or a `m[k]++` rule, so the default is written where it is used and nothing invents a zero value. `d` is always evaluated, like every argument. Would change if a different name (`get`, `lookup`) reads better.
- **`==` compares contents** for structs, lists, maps and enums; errors are equal when their messages are; interfaces compare dynamic type and value. Channels and function values have no `==`.
- **Strings can hold any bytes.** Files, sockets and hashes use `string` for raw data.
- **`string()` exists on `int`, `float`, `bool`, `byte` and `string` only.** `byte.string()` gives the number (`"97"`); text from bytes is `string([]byte)`. Lists and maps have no text form.
- **Every enum has a built-in `name()`**, the name of the value's case (`"North"`, `"Circle"` for `Shape.Circle(2.0)`: the case only, not the data). It is `name()` rather than `string()` because it is not a full text form for enums with data, and those often write their own `string()`. An enum cannot declare a method `name` (one method name means one thing), and the built-in method satisfies an interface's `name() string`, so an enum implementing such an interface needs no hand-written switch.
- **Bytes have bitwise operators but no arithmetic;** convert with `int(b)`.
- **Shifts:** the count has the operand's type (`b << byte(1)`) and a negative count crashes; `int` shifts never overflow and `>>` rounds toward negative infinity; `byte` shifts keep the low 8 bits.
- **List operations crash out of range:** `xs[i]`, `xs[i] = v` (which never grows the list), `insert` (`0 <= i <= len`), `remove` and `slice` (`0 <= a <= b <= len`), like their string counterparts.
- **String operations are methods** (`s.split`, `s.trim`, `s.toInt()`, ...), and `xs.join(sep)` is a method on `[]string`. Extra helpers are in the `strings` package.
- **Float division by zero gives `inf`/`nan`;** only integer division by zero crashes.
- **A struct cannot contain itself by value;** use a `T?` field, a list or an enum.
- **Struct fields may declare a default value** (`int timeout = 0`), and a struct literal may leave such a field out. A field without a default must still be set, so there are still no zero values: every value is written somewhere, in the literal or once in the type. The point is growing a struct that other code builds: adding a field with a default breaks no literal (see `http.Request.timeout`). The rules, chosen to keep a literal free of hidden behaviour:
  - **A default is computed like a constant:** literals, constants (the struct's package's, private ones too, evaluated in that package's scope), enum values, named functions, operators, conversions, built-in methods that only compute a value, and list, map and struct literals; no calls of functions or methods, no variables or other fields, no `try`, `group` or new channel. So a literal that uses a default runs no program code, cannot block, cannot fail (beyond what a constant can: an index out of range) and has no effects. Calls of "pure" functions were left out because Seed cannot tell a pure function from one that prints or reads a file; would change if it could, or if defaults computed by a constructor function turn out to be needed (a function returning the struct is the way today).
  - **Evaluated at every literal that leaves the field out**, after the values the literal writes, exactly as if it were written in the literal: each literal gets its own list or map, and a default that names a constant (`[]string tags = standardTags`) shares the constant's value copy-on-write, like any use of a constant. A crash in a default (an index out of range) is reported at the default's position, in the function whose literal used it.
  - **A default that uses itself** through struct literals that leave fields out (`Node? next = Node{}`) is an error (`the default value of Node.next uses itself: Node.next -> Node.next`).
  - **Defaults are part of the public API**: a literal in another package gets them. Such a literal still needs every field to be `pub`, defaulted ones included, so a private field with a default does not let other packages build the struct (handles stay unforgeable). Would change if private defaulted fields should be allowed to stay out of other packages' literals.
  - **Only struct fields** have defaults: not function parameters (no default arguments, one way to call a function) and not enum case fields. There are no positional struct literals, so the question of defaults in them does not arise.

## Null and errors

- **Narrowing works on variables and their fields** (`u.email`), through `&&`, `||`, `!`, after an `if` that always leaves, and after `assert` in tests. List elements and map lookups must be stored in a variable first.
- **Narrowing on assignment:** after `x = <non-null value>`, `x` is a `T` until it may become null again (`if (x == null) { x = "default" }` leaves `x` non-null).
- **Narrowing ends** when the path is assigned a value that may be null, when a part above it is assigned or has a `mut` method called on it (`u.reset()` for `u.email`), and before a loop that changes it. A `mut` method on the narrowed value itself (`xs.push(x)`) keeps it narrowed: the receiver is a plain `T` inside the method.
- **A `T?` compares with `null` or with a `T`**: for `int? n`, `n == 2` is false when `n` is null and `n != 2` is true, for every `T` that has `==`, so `counts["a"] == 3` needs no variable. Two `T?` values do not compare with each other (whether two nulls are equal is rarely the question; narrow them first), and a comparison with a value does not narrow. Inside lists, structs and enums, nullable parts compare as part of the container.
- **`error?` is not a type,** because `error` is already nullable (like `T??`).
- **`error` is narrowed like a `T?`.** `err.message()` compiles only where the compiler sees that `err` is not null (the same flow-sensitive rules: checks, early returns, `&&`/`||`, `assert` in tests, assignments of an error known not to be null or of a value of a type that implements `error`), so "no nil" holds for errors too and the run-time crash `message() called on a null error` cannot happen in checked code. The cost is a check where the programmer knows better: a call result such as `errors.new("x")` is a plain `error` and must be stored and checked before `message()`. Would change if a non-null error type were added.
- **Error guards:** a plain `T` returned beside an error can be read only once the error is known to be null (`if (err == null)`, after `if (err != null) { return ... }`, right of `err == null &&`), or after it is assigned again. A `T?` beside an error is not guarded.
- **Only a local variable can receive a plain `T` beside an error;** a field or element can't (`b.s, err = f()`), because it would hold null until the check. A `T?` field or element can.
- **Every result must be used,** not only errors: discard with `_ = f()`. A value beside a discarded error must be declared `T?`. A typed `_` (`string _, int _, error err = f()`) discards like `_`, any number of times, and `error _` discards the error like `_` does.
- **`return null, null` for a plain `T` result is an error;** `return null, err` with an `err` that turns out to be null crashes (`f returned null as result 1 without an error`).
- **`try` works anywhere in an expression** in a function whose last result is `error`, including `try group {...}`.
- **Crash vs error exit codes:** an error returned from `main` exits with 1 (`error: ...`), a crash with 2 (`crash: ...`).
- **A crash shows where it happened and the calls that led there**, below its message, innermost first, one line each: `    at f (file:line:col)` for the crash, `    called from g (file:line:col)` for each call (the caller and the position of the call), and for a goroutine `    spawned from h (file:line:col)`, the position of its `spawn` (only that one, not the spawner's own callers). Function names are Seed's: `get`, `Cart.add`, `cart.newCart` and `cart.Cart.add` outside package `main`, `test "name"`; paths are as given to the compiler, the standard library's from `lib/` on; the column is the operation's (the call, the operator, the indexed value). A deep stack (a stack overflow) shows its first 10 and last 5 calls with `    ... N more calls ...` between them. The format is Go's (`goroutine 1 [running]: main.get(...) main.go:6`) made shorter: no addresses, no goroutine numbers. A crashed goroutine's error keeps the message `crash: <message>`, so error equality and printing are unchanged; the trace travels with that error value, and is printed below `error: crash: ...` when `main` returns it, and below the `FAIL` line of a test that crashed. Calls that the C compiler inlined are not shown (the crash's own position always is); `seed run -g` shows them all. Would change if the trace should be part of the message (then two crashes at different places would be different errors), or if every goroutine's spawn chain should be kept (a cost at every `spawn`).
- **`os.crash(message)`** crashes the goroutine like a runtime fault, so library code can report a caller's mistake.
- **No type switches on interfaces.** Errors are told apart by message or by returning richer results.

## Functions, methods and interfaces

- **A parameter can be assigned a new value, but not changed in place.** `args = args.slice(1, args.len())` changes only the function's copy (values only, so the caller never sees it), as in Go. `mut` methods on a parameter and assignments to its fields or elements stay errors, because in Go they would reach the caller's slice or map and a Go programmer would expect them to; the compiler says so instead of silently changing a copy. The receiver of a method that is not `mut` stays read-only (only a `mut` method changes its receiver). An assigned parameter owns a copy of its value from the function's entry (compiler/README.md, "Memory management").
- **Interface satisfaction is explicit** (`implements`) and needs the exact signature, including `mut`. Structs and enums can implement interfaces; methods cannot be declared on interface types.
- **A type that implements an interface converts to it automatically,** and to the nullable interface; a type that implements `error` converts to `error`.
- **Interface methods can be `mut`;** calling one needs a variable (or a part of one) and changes that interface value only.
- **A struct field of function type is called directly:** `op.apply(1, 2)`. A struct can't have a field and a method with the same name (a compile error), so `op.apply` always means one thing.
- **Unused parameters and unused package-level declarations are allowed;** unused locals, pattern bindings and imports are errors.

## Control flow

- **`switch` over an enum cannot have `default`;** every case must be listed, so adding a case points at every `switch` to update.
- **`switch` works on enums, `int`, `byte`, `string` and `bool` only.**
- **`switch` over `int`, `byte`, `string` or `bool` must end with `default`:** `default` is the last case (a `case` after it is an error), and one `case` can list several values.
- **Enum case patterns match the case exactly:** every field bound with its type (`_` to ignore one), no parentheses for a case without data, and only `_` bindings in a `case` with several labels.
- **Defers run last-first,** like Go, and also when the goroutine crashes or is stopped; `os.exit` and a deadlock skip them.
- **`defer` takes a call of a function, method, function value, interface method or package function, or `ch.close()`**, but not a `mut` method (its variable is gone when the call runs). A deferred error must be discarded: `defer _ = f.close()`.

## Concurrency

- **`group { ... }` is an expression of type `error`,** used only whole: `error err = group {...}`, `err = ...`, `return ...`, `_ = ...` or `try group {...}`.
- **A group block cannot be left early** (`return`, `try`, `break`/`continue` out of it), because the group must wait for its goroutines first.
- **`spawn` can appear anywhere inside a `group` block,** including loops. It takes the same calls as `defer` (no `mut` method), returning `error` or nothing; the receiver and arguments are deep-copied.
- **When a group fails, only its goroutines are stopped,** not the code of the block itself; the block should spawn and leave waiting to goroutines or to the code after the group.
- **Stop points** are channel operations, `select`, `time.sleep` and the blocking standard-library calls (stdin, reads of an `fs.File`, network, `os.run`, `os.output`, waiting for another goroutine's operation on the same handle), so a stopped server doesn't hang in `accept`. Other file operations (`fs.read`, `fs.write`, `f.write`, ...) don't block for long on regular files and are not stop points, nor is `ch.close()`.
- **Channels are the one reference type.** Copying a channel gives another handle to the same channel (reply channels inside messages).
- **Channel elements cannot be nullable** (`chan (int?)`), because `receive()` uses null for "closed"; `chan int?` is a nullable channel. A `chan error` receives `error`.
- **Select cases** are `ch.send(v)`, `ch.receive()`, `_ = ch.receive()`, `T? v = ch.receive()` (a new variable; `error e = ch.receive()` for a `chan error`) and `v = ch.receive()`, which assigns an existing variable or parameter of exactly the received type, following the rule of declarations and assignments (a typed name is declared, an untyped one assigned). A field or element cannot receive directly (its place would be evaluated after the select chose the case). On a `chan error`, `case ch.receive():` is an unhandled error: declare it or write `case _ = ch.receive():`. All channels and values are evaluated, in order, before select waits. `select` with `default` is an error with a hint to use a timeout channel.
- **`time.after(d)` sends the time once and closes the channel.**
- **Deadlock is a crash:** when every goroutine is blocked and no timer is pending, the program prints `crash: deadlock: all goroutines are blocked` and exits with 2, without running defers.

## Packages, visibility and tests

- **Imports are per file,** and resolved in the standard library first, then relative to the project root (the directory of `package main`, or the one given to `seed test`). There is no project file; importing a project package that has a standard library package's name is an error at the import (rename the package).
- **A package's name is its directory's name** (only `package main` differs), and `main` can't be imported.
- **Struct fields are private unless `pub`,** so no program can forge a file or socket handle; a struct literal of another package's type needs every field to be `pub`. Enum cases and interface methods are as visible as their type; methods need `pub`.
- **A local or package-level name can't take an imported package's name.**
- **The core packages (`fmt`, `os`, `fs`, `errors`, `time`) are ordinary standard library packages** and must be imported.
- **Tests:** `test "name" { ... }` blocks in the package's `tests/` directory; the body works like a function returning `error` (`try` works, `return` doesn't); `assert` only in tests (not in a group), showing both sides of a failed comparison as `.string()` gives them (a byte as its number).
- **`seed test` runs each test in a goroutine of its own group,** one after the other, prints `FAIL "<name>": <where>: <reason>` per failure and `N passed, M failed`, and exits with 1 on any failure.

## Standard library

- **Natives:** standard library functions can be declared without a body and written in C (`lib/<pkg>/<pkg>.c`, `sd_lib_<pkg>_<name>`); only the standard library may do this.
- **Error messages follow one form:** `<package>.<function>: <subject>: <reason>`, e.g. `fs.read: notes.txt: no such file or directory`, `string.toInt: "x": invalid integer`.
- **The package set** is `errors fmt io os fs path strings regex math rand time encoding json csv url crypto net http flags log`, as designed in docs/stdlib.md; all of it is implemented. `regex`, `csv`, `url`, `flags` and `log` were added after the first design, as the most common gaps for real programs.
- **An HTTP request's time limit is a field, `http.Request.timeout`, with the default 0** (struct fields have default values, so the field breaks no existing literal). A positive timeout limits the whole exchange of `http.send`, from connecting to the last byte of the response, in nanoseconds like the rest of `time`; the error is `http.send: <url>: timeout after 2 s`. 0 means no limit on the whole exchange, with the 30 seconds without progress per step that `send` always had: a default of 30 s for the whole exchange was rejected because it would silently cut off large or slow downloads that work today. A negative timeout crashes (like `net.dial`'s). The field means nothing on the requests a server receives, which have 0. The other fields of `Request` (`method = "GET"`, `headers`, `body`) and of `Response` (`headers`, `body`) have defaults too, so `http.Request{url: u}` is a GET and `http.Response{status: 204}` an empty response; `url` and `status` must be written. `http.getWithin(url, timeout)` and `http.sendWithin(req, timeout)`, which came first, stay as thin wrappers (the same exchange, errors named after them, a crash for a timeout that is not positive): `getWithin` is still the one-line form for a GET, and removing them would break programs for no gain. Would change if "one way to do things" should win over compatibility: then `sendWithin` goes. Giving up for other reasons than time is still done with a group.
- **`time.Date`'s time of day defaults to midnight** (`hour`, `minute`, `second` and `nanosecond` default to 0), so a calendar date is `time.Date{year: 2026, month: 10, day: 15}`. The other standard-library structs got no defaults: `fs.Info` is only returned, and `net`, `fs` and `rand` handles have private fields.
- **`regex` copies Go's `regexp` (RE2), not Perl or Python.** Linear-time matching is worth more than backreferences and lookaround, and one well-documented dialect beats a new one: the syntax, leftmost-first semantics, the empty-match rules of `findAll` and `split`, `(?i)`'s Unicode case folding and the `\p{...}` tables are Go's, checked against Go on thousands of generated cases. Deliberate differences: duplicate group names are an error (Go accepts them; `named` would be ambiguous); in a replacement template `$1x` is group 1 then `x` (Go reads a group called `1x` and substitutes nothing); a truncated UTF-8 sequence is not matched by `.` (Go matches its first byte as U+FFFD). Would change if Perl-style features were wanted at the cost of the linear-time guarantee.
- **A `regex.Regex` is plain data (the pattern, an id, the group names); the compiled form lives in a per-goroutine cache keyed by the id.** Values are copied and deep-copied between goroutines, so a Regex cannot own native memory, and a handle in a process-wide table (as `fs.File` is) would never be freed, since handles are not closed when their last copy disappears. The cost: a goroutine recompiles a pattern the first time it uses it, and one that alternates between more than 16 regexes recompiles often. Would change if the runtime gained values with native finalizers.
- **`regex` names:** `Match.groupText(i)` rather than `group(i)`, because `group` is a keyword; `matches` (a `bool`), `find`/`findAt`/`findAll`, `replace` (templates), `replaceLiteral`, `replaceWith` (a function value) and `split`; `mustCompile` for patterns written in the program, which crashes like any caller's mistake. Template mistakes crash too (`$` at the end, a missing group): templates are written in programs, not read from users.
- **`csv` takes the delimiter as a parameter of every function** (`csv.parse(text, ',')`) instead of an options struct: struct literals must set every field, so an options struct would make every call longer, and explicit is the house style. Reading is Go's `encoding/csv` with its defaults (strict quotes, empty lines skipped, `\r\n` folded); records may have different lengths in `parse`, and `parseMaps` checks them against the header. Streaming is line by line (`Reader.feed(line)`) because Seed has no reader interface: lines come from `fs.File.readLine`, `io.readLine` or anywhere else. `format` ends records with `"\n"`, as Go does by default; RFC 4180's `"\r\n"` is a join of `formatRecord`'s lines.
- **`url` keeps every part as written (percent-encoded)** and decodes on request (`pathDecode`, `queryDecode`), unlike Go's `URL.Path`, which loses the difference between `%2F` and `/`. Absent parts are `null`, so an empty query and no query differ. `parse` rejects spaces and control characters (Go accepts spaces). Queries are ordered lists of `Param`, not maps (Go's `Values` is a map and `Encode` sorts), so building a query keeps the order it was written in. `http` is unchanged: integrating it with `url` would mean refactoring its client and `Request.query()`.
- **`flags` returns a value instead of binding variables.** Go's `flag.Int(&n)` needs pointers; Seed has none and no closures, so a `Spec` value declares the flags with `mut` methods, `parse` returns a `Parsed` value, and typed getters (`getInt("count")`) read it by name. A misspelled name or the wrong getter crashes immediately, which is as good as a compile error for a program that runs its own `main` once in a test. The alternatives were a user struct filled by reflection (there is none) or one callback per flag (no closures to capture the target). The syntax is GNU's (`--long`, `-s`, bundles, `--`) rather than Go's single-dash long flags, and flags may follow arguments; `parseOrExit` exits 0 after `--help` and 2 on a mistake, as command-line tools do.
- **`log` has no default logger:** with no package-level variables, a `Logger` is a value made in `main` and passed down (`log.new(level, output)`, with copies sharing the output). Fields are added with `with(key, value)`, which returns a new Logger, rather than a variadic `info(msg, k1, v1, ...)` (there are no variadics) or a map argument on every call. The line format is `log/slog`'s text handler (`time=... level=INFO msg=... k=v`), in UTC with milliseconds. A `Lines(chan string)` output, and `withClock`, make logs testable.
- **An HTTP request's time limit is a function, `http.sendWithin(req, timeout)` (and `http.getWithin(url, timeout)`), not a `timeout` field of `http.Request`.** A struct literal must set every field, so a new field would break every `http.Request{...}` already written (programs, tests, the docs) and would mean nothing on the requests a server receives; a second pair of functions beside `get`/`send` breaks nothing. The limit covers the whole exchange, from connecting to the last byte of the response, in nanoseconds like the rest of `time`, and must be positive (a crash otherwise, like `net.dial`'s negative timeout); the error is `http.sendWithin: <url>: timeout after 2 s`. `get` and `send` keep their 30 seconds without progress per step; giving up for other reasons than time is still done with a group. A field would be the better shape if struct fields ever get default values.
- **`io.read(max)`** reads between 1 and `max` bytes of stdin (null at the end), sharing the buffer with `readLine` and `readAll`, like `fs.File.read`: input that is not made of lines (the language server's messages: a header, then a body of a given length) needs it.

## Toolchain and compiler

- **The pedantic checks and the formatting check are always on;** there are no flags or warnings. Unformatted code is an error at the first differing line, with the hint `run: seed fmt <file>`.
- **Nesting limit:** blocks and expressions nest at most 256 levels deep; deeper code is a compile error (it would overflow the compiler's or the C compiler's stack).
- **Commands:** `seed build [-g] [-o out]`, `seed run [-g]` (a `--` before the program's arguments is skipped), `seed test`, `seed fmt [--check]`, `seed lsp`, plus `seed c` and `seed ast` for debugging. `seed fmt` takes files and directories: a directory means every `.sd` file under it, subdirectories included, skipping hidden directories (`.git`), so a project is `seed fmt .`, as with `gofmt -w .` and like `seed test`, which also takes directories. `seed` finds its root from its real path (symbolic links resolved) unless `$SEED_ROOT` is set.
- **`seed build -g` and `seed run -g` are for debuggers:** the C has `#line` directives that point at the Seed source (absolute paths, so a debugger finds them from anywhere) and is compiled with `-g -O0`, so gdb and lldb break, step and backtrace by Seed lines and functions; locals keep their C names (`l_x`, or `L.l_x` in the cleanup frame), and `runtime/seed-gdb.py` adds pretty printers and a `seed-locals` command to gdb. `seed c -g` prints that C. Would change if a debugger should see Seed names directly (that needs DWARF of our own rather than the C compiler's).
- **`args[0]` is the program itself.**
- **Messages anticipate Go habits.** Besides `:=`, `var`, `nil` and Go's built-ins, `fmt.printf` (and `sprintf`, `errorf`, ...) gets the hint that Seed has no format strings (`+` and `.string()`, or `fmt.fixed`), and a `(T, error)` call used as one value suggests `try` before the declaration of both results.
- **The language server is part of the `seed` binary** (`seed lsp`, written in Seed with the compiler's own loader, checker and formatter), so an editor's diagnostics are exactly the compiler's: it checks each open document's package as `seed build` or `seed test` would, with the editor's unsaved text, reports the formatting check as a warning rather than an error, and answers definition, hover, completion, document symbols and formatting. Each request runs in a goroutine of its own, so a compiler crash on half-written code loses that answer, not the server.
- **The formatter keeps the source's line structure:** no maximum line length, `{}` for empty blocks, trailing comments not aligned, one-line `const`s may stay grouped (docs/formatting.md).
- **Seed compiles to C,** with the runtime (`runtime/`, written in C) pasted into every program, and uses the system C compiler.
- **Bootstrap:** the C bootstrap compiler `seed0` (64-bit ints, a subset of the language) compiles the compiler once; it has been retired: the compiler is now built from a C snapshot of itself (`bootstrap/seed.c`), refreshed with `make release`.
